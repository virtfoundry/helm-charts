# CRDs and upgrades

VirtFoundry keeps its state in `virtfoundry.io` custom resources: tenants, instances, networks, templates, VKS clusters and more. The CRDs define those kinds, so how they are installed and upgraded matters.

!!! danger "Deleting a CRD deletes its data"
    Removing a CRD removes every custom resource of that kind. Deleting `tenants.virtfoundry.io` deletes all tenants. Never delete these CRDs to "reset" an install.

## The problem with Helm

Helm installs files in a chart's `crds/` directory on the **first install only**. It does not upgrade or delete them. A new field in a CRD never reaches a cluster through `helm upgrade`, and the API server then drops the field or rejects the resource.

## The `virtfoundry-crds` chart

All 16 CRDs live in one chart, `charts/virtfoundry-crds`, in `templates/` so that `helm upgrade` updates them. Each one is protected:

| Protection | Stops |
|------------|-------|
| `helm.sh/resource-policy: keep` | `helm uninstall` deleting the CRD |
| `argocd.argoproj.io/sync-options: Prune=false,Delete=false` | Argo CD pruning the CRD, or deleting it with the Application |

The CRD files are copied verbatim from their sources of truth, so they are never parsed as templates:

| CRDs | Source of truth |
|------|-----------------|
| 15 platform CRDs | [`virtfoundry/operator`](https://github.com/virtfoundry/operator) (generated by controller-gen) |
| `VKSCluster` | [`virtfoundry/vks`](https://github.com/virtfoundry/vks) |

CI fails when `charts/virtfoundry-crds/manifests` drifts from those sources (`make verify-crds-chart`). To refresh after a CRD change upstream:

```bash
make sync-crds-chart   # copies from operator and vks main
git diff charts/virtfoundry-crds/manifests
```

## Install order

With the CRD chart, CRDs come first and are a separate release:

```bash
helm install virtfoundry-crds virtfoundry/virtfoundry-crds \
  --version 0.10.0 -n virtfoundry-system --create-namespace

helm install virtfoundry-operator virtfoundry/virtfoundry-operator \
  --version 0.10.0 -n virtfoundry-system --skip-crds
```

`--skip-crds` is needed while the operator chart still ships its own `crds/` directory, otherwise Helm reports that the CRDs already exist.

!!! note "Status"
    The CRD chart is in the repository and is published with the next release. Until the operator chart stops shipping `crds/`, **the install in [Installation](installation.md) is unchanged**: the operator chart installs the CRDs and you upgrade them by hand (below).

## Upgrading CRDs today (operator chart)

Apply the CRDs from the new chart version before upgrading the releases. Server-side apply is required: the CRDs are too large for the client-side annotation.

```bash
helm pull virtfoundry/virtfoundry-operator --version <new> --untar
kubectl apply --server-side --force-conflicts -f virtfoundry-operator/crds/
helm upgrade virtfoundry-operator virtfoundry/virtfoundry-operator --version <new> -n virtfoundry-system
```

The `VKSCluster` CRD is part of the `virtfoundry-vks` chart templates, so `helm upgrade` of that chart updates it.

## Adopting existing CRDs into the CRD chart

For a cluster that already has the CRDs (installed by the operator chart), tell Helm the new release owns them. Do this once, before the first `helm install` of `virtfoundry-crds`:

```bash
for crd in $(kubectl get crd -o name | grep '\.virtfoundry\.io$'); do
  kubectl annotate "$crd" meta.helm.sh/release-name=virtfoundry-crds \
    meta.helm.sh/release-namespace=virtfoundry-system --overwrite
  kubectl label "$crd" app.kubernetes.io/managed-by=Helm --overwrite
done
```

This changes metadata only. No CRD content changes and no custom resource is touched. Then install `virtfoundry-crds` and the operator chart with `--skip-crds`.

## Argo CD

- Set `ServerSideApply=true` on the Application that installs the CRDs (large CRDs overflow the client-side annotation).
- Install the CRD Application first, with an earlier sync wave than the operator.
- The `Prune=false,Delete=false` option is already on every CRD, so removing the Application leaves them in place.

## What this does not solve

- **Destructive schema changes** (removing a field, changing a type) still need a migration plan and, for stored objects, a conversion step. The chart only delivers the new schema.
- **Order matters on upgrade:** apply the CRDs first, then the controllers that use new fields.

See also [Troubleshooting](troubleshooting.md#new-crd-field-is-ignored-after-a-chart-upgrade).
